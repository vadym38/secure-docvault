Cipher vault / data at rest

Три частини контейнера — один автентифікований файл.

AES-256-GCM шифрує вміст і одночасно обчислює 16-байтний Auth Tag. Для кожного файлу генерується новий 96-бітний IV. Навіть якщо диск, бекап або каталог instance/vault викрадено, без ключа залишається лише нечитабельний ciphertext.

01 · Nonce

IV / Nonce

os.urandom(12) для кожної операції. Повторне використання IV з одним ключем ламає GCM.

12 B
02 · Integrity

Auth Tag

Обчислюється GCM над ciphertext + AAD. Будь-яка зміна байта → InvalidTag.

16 B
03 · Confidentiality

Ciphertext

Той самий розмір, що й plaintext. Не містить імені файлу, MIME-типу чи метаданих.

N B

Модель загроз

Викрадення диска / бекапуБез ключа — лише ciphertext; ключ зберігається окремо в FILE_ENCRYPTION_KEY.
Модифікація 1 байтаGCM tag не збігається → InvalidTag → 409, файл не видається.
IDOR / перебір UUIDUUID4 + перевірка owner/admin; AAD прив'язує контейнер до документа.
Підміна контейнераAAD містить document_id та owner_id; чужий tag не підійде.
Висновок: AES-256-GCM дає одночасно конфіденційність і цілісність, але вимагає унікального IV, захищеного ключа та перевірки прав. У Secure DocVault це поєднано з атомарним записом, SHA-256, AAD та контролем власника; WAF, CSP і санітизація з ЛР №3–4 залишаються окремими шарами Defense in Depth.
